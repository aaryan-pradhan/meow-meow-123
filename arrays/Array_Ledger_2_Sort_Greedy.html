Sort + Greedy

Nine problems where the whole solution is sort, then take one pass. Sorting is never the answer here — it is what makes a local rule safe: once the array is ordered, the extreme element can be resolved immediately, a failed comparison can never be rescued by a later element, and an adjacent-swap argument becomes a total order. Reach for this page when an optimisation problem has no visible structure but a single comparison between two elements decides which of them should come first.

Recognition rules

The judgment calls that separate these problems from each other. Every rule must be demonstrated by at least two entries on this page.

1

Two pointers come in two shapes. Converging (\(i=0, j=n-1\)) when pairing elements within one array — Ferris Wheel, and the inner loop of Sum of Three Values. Parallel (both start at 0) when matching between two arrays — Apartments. Ask "am I pairing a list with itself, or with another list?" before choosing.

2

Sorting is free only when positions don't matter. Ferris Wheel and Stick Lengths print a number, so the array is sorted in place. Sum of Three Values must print original 1-based positions, so the index rides along inside pair<value,index> and the output reads v[i].sc, never the loop counter. Check the output format before typing sort.

3

"Does some X fit?" is not "can all X be matched?" — a resource used once must be consumed. Apartments cannot binary-search each applicant independently (two applicants would claim the same flat); Sum of Four Values needs the explicit a!=i && a!=j && b!=i && b!=j guard because the stored pair may reuse an index it already spent.

4

When the objective is \(\sum \text{position} \times \text{value}\), the sort direction falls out of an adjacent swap. Reducing Dishes maximises, so large values must take large multipliers → ascending. Tasks and Deadlines minimises \(\sum (n-k+1)\cdot a_{k}\), so small values take large multipliers → also ascending, but for the opposite reason. Write the two-element comparison first; the order is whatever it says.

5

Before sorting, check whether a closed-form bound already answers it. Reading Books is \(\max (\sum t, 2\cdot t_{\max})\) in one unsorted pass — two lower bounds that happen to be jointly achievable. Stick Lengths only needs the sorted order to locate the median (an nth_element would do), and Missing Coin Sum only needs it to justify breaking early. Sorting is the scaffold for the proof more often than it is the computation.

6

Answer width, every time: \(2\cdot 10^{5}\) values of \(10^{9}\) is \(2\cdot 10^{14}\) — Stick Lengths and Reading Books both overflow int on the accumulator alone, and Tasks and Deadlines reaches \(\approx 2\cdot 10^{16}\) because its sum is of prefix sums. Only Ferris Wheel's and Apartments' answers (counts bounded by n) actually fit in 32 bits.

1 · Sort + two-pointer greedy matching

Sort, then sweep with one pointer per end (or one per array) instead of testing every element against every other. What makes it work is always the same: after sorting, the element at a pointer is the extreme unresolved one, and its fate is decided this step — either it is matched, or it can be discarded forever. Each step advances a pointer, so the sweep is linear and the sort dominates.

Ferris Wheel

\(O(n \log n)\)
The ask

Question. There are \(n\) children with weights \(p_0, \dots, p_{n-1}\). Each gondola carries one or two children, and their total weight must not exceed \(x\). What is the minimum number of gondolas needed?

Input
\(n,\ x\), then \(p_0, \dots, p_{n-1}\).
Output
One integer: the minimum number of gondolas.
Limits
\(1 \le n \le 2\cdot 10^5,\ \ 1 \le x \le 10^9,\ \ 1 \le p_i \le x\)
Sample
\(x = 10\), weights 7 2 3 9 → 3
Breakdown
  1. State it exactly: split the children into groups \(S\) of size 1 or 2: \[ \min |\mathcal{P}| \quad \text{subject to} \quad |S| \le 2,\ \ \sum_{k \in S} p_k \le x \ \ \text{for every } S \in \mathcal{P} \]
  2. Sort so that \(p_0 \le p_1 \le \dots \le p_{n-1}\). The heaviest child \(p_j\) needs a gondola now. The only question is who joins.
  3. If anyone fits with \(p_j\), the lightest \(p_i\) fits. Swapping the lightest in never hurts: \[ p_i + p_j \le x \;\Longrightarrow\; \text{pair } (i, j); \qquad p_i + p_j \gt x \;\Longrightarrow\; j \text{ rides alone} \]
  4. Simplest form, two pointers \(i = 0,\ j = n-1\): \[ \text{while } i \le j:\ \ \text{if } p_i + p_j \le x \text{ then } i{+}{+};\quad j{-}{-};\quad \text{count}{+}{+} \]
Key observations
  1. The heaviest unseated child rides in this step no matter what. The only open question is whether someone joins them.
  2. If anyone fits with the heaviest, the lightest fits too. Pairing heaviest with lightest is never worse: it keeps the heavier light children free for later.
  3. If the lightest does not fit with the heaviest, nobody does, so the heaviest rides alone.
  4. Both cases use up the heaviest and cost one gondola, so j-- and count++ always run. Only i++ depends on the test.
  5. \(i = j\) (one child left) needs no special case: one gondola is charged either way.
Brute force → why it dies
naiveSearch all groupings, or rescan the remaining children for the best partner of the current heaviest.
cost \(O(n^2)\) for the rescan; exponential for the search.
dies at \(n = 2\cdot 10^5\) gives about \(2\cdot 10^{10}\) comparisons for the rescan alone.
therefore Sort once and move two pointers inward: \(O(n \log n)\) total, \(O(1)\) extra space.
Diagram
Implementation

The loop body is three lines and only the first is conditional. j--; count++; sit outside the if because the heaviest child is resolved either way — the misread is to expect an else branch. The loop condition is i <= j, not i < j, so the final lone child is still charged a gondola.

// Problem: Ferris Wheel
// Link: CSES 1090
// Pattern: sort, two-pointer from both ends — pair lightest with heaviest
// when they fit together, else heaviest rides alone
// Time: O(n log n)  Space: O(1) extra
//
// n children, gondola holds 1 or 2, total weight per gondola <= x. Minimum
// gondolas needed.
//
// Example:
//     7 2 3 9, x=10 -> 3

#include <iostream>
#include <vector>
#include <algorithm>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int n;
    long long x;
    cin >> n >> x;

    vector<long long> p(n);
    for (int i = 0; i < n; i++) cin >> p[i];

    sort(p.begin(), p.end());

    int i = 0, j = n - 1, count = 0;
    while (i <= j) {
        if (p[i] + p[j] <= x) i++;
        j--;
        count++;
    }

    cout << count << '\n';
    return 0;
}
import sys
tok = iter(sys.stdin.read().split())

def main():
    n, x = int(next(tok)), int(next(tok))

    p = [int(next(tok)) for _ in range(n)]

    p.sort()

    i, j, count = 0, n - 1, 0
    while i <= j:
        if p[i] + p[j] <= x: i += 1
        j -= 1
        count += 1

    print(count)

Gotchaj-- and count++ fire on every iteration, pairing or not. Writing if (fits) { i++; j--; count++; } else { j--; count++; } is the same thing spelled twice; writing else j--; and forgetting count++ silently undercounts the solo riders.
Recognize"minimum number of groups of at most two, under a per-group capacity" → sort, converge from both ends, always consume the extreme.

Apartments

\(O(n \log n + m \log m)\)
The ask

Question. There are \(n\) applicants and \(m\) apartments. Applicant \(i\) wants size \(a_i\) and accepts any apartment whose size is within \(k\) of it. Apartment \(j\) has size \(b_j\). Each applicant gets at most one apartment and each apartment goes to at most one applicant. How many applicants can get an apartment?

Input
\(n, m, k\); then \(a_0..a_{n-1}\); then \(b_0..b_{m-1}\).
Output
One integer: the maximum number of matched applicants.
Limits
\(1 \le n, m \le 2\cdot 10^5,\ \ 0 \le k \le 10^9,\ \ 1 \le a_i, b_j \le 10^9\)
Sample
\(k = 5\), \(a =\) 60 45 80 60, \(b =\) 30 60 75 → 2
Breakdown
  1. State it exactly: a matching \(M\) pairs applicants with apartments, one-to-one: \[ \max |M| \quad \text{subject to} \quad |b_j - a_i| \le k \ \ \text{for every } (i, j) \in M \]
  2. Sort both lists ascending. Give each applicant the smallest apartment that fits. A larger one that also fits is better kept for a later, larger applicant.
  3. Compare the smallest unmatched applicant \(a_i\) with the smallest unused apartment \(b_j\): \[ b_j \lt a_i - k \Rightarrow j{+}{+}, \qquad b_j \gt a_i + k \Rightarrow i{+}{+}, \qquad \text{else match: } i{+}{+},\ j{+}{+} \]
  4. Simplest form: each step moves at least one pointer, so the scan takes \(n + m\) steps after the two sorts.
Key observations
  1. A match uses up an apartment. Asking "does some apartment fit applicant \(i\)?" separately for each applicant can count the same apartment several times.
  2. Sort both sides and give each applicant the smallest apartment that fits. Any larger fitting one is better saved for a larger applicant (exchange argument).
  3. If \(b_j \lt a_i - k\), the apartment is too small for this applicant, and so for every later (larger) one. Discard it: j++.
  4. If \(b_j \gt a_i + k\), the apartment is too big for this applicant, but a later one may take it. Discard the applicant: i++.
  5. Every step moves at least one pointer, so the scan is \(O(n + m)\) and the sorts dominate.
Brute force → why it dies
naiveFor each applicant, scan all apartments for a free one in range.
cost \(O(n \cdot m)\).
dies at \(n = m = 2\cdot 10^5\) gives \(4\cdot 10^{10}\) checks. A binary search instead of the scan is faster but wrong: it never marks the apartment as taken.
therefore Sort both and sweep one pointer per side: \(O(n \log n + m \log m)\), \(O(1)\) extra.
Diagram
Implementation

One while with a three-way branch, and the asymmetry between the first two branches is the whole algorithm: a too-small apartment advances j (discarded permanently), a too-big apartment advances i (the apartment survives for a later applicant). Only the third branch advances both. k is read as long long so a[i] - k is evaluated in 64-bit.

// Problem: Apartments
// Link: CSES 1084
// Pattern: sort both sides, two-pointer greedy sweep
// Time: O(n log n + m log m)  Space: O(1) extra
//
// n applicants each want a size in [a_i - k, a_i + k], m apartments each of
// fixed size. Maximize the number of applicants matched to a distinct
// apartment.
//
// Example:
//     a = 60 45 80 60, b = 30 60 75, k=5 -> 2

#include <iostream>
#include <vector>
#include <algorithm>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int n, m;
    long long k;
    cin >> n >> m >> k;

    vector<long long> a(n), b(m);
    for (int i = 0; i < n; i++) cin >> a[i];
    for (int i = 0; i < m; i++) cin >> b[i];

    sort(a.begin(), a.end());
    sort(b.begin(), b.end());

    int i = 0, j = 0, count = 0;
    while (i < n && j < m) {
        if (b[j] < a[i] - k) j++;
        else if (b[j] > a[i] + k) i++;
        else { count++; i++; j++; }
    }

    cout << count << '\n';
    return 0;
}

tok = iter(sys.stdin.read().split())

def main():

    a = [int(next(tok)) for _ in range(n)]
    b = [int(next(tok)) for _ in range(m)]

    a.sort()
    b.sort()

    i, j, count = 0, 0, 0
    while i < n and j < m:
        if b[j] < a[i] - k: j += 1
        elif b[j] > a[i] + k: i += 1        # else if -> elif
        else: count += 1; i += 1; j += 1

    print(count)

GotchaThe two discard branches are not symmetric — getting them the wrong way round (advancing i when the apartment is too small) throws away applicants who could still be housed. Both branches are only valid because both arrays are sorted ascending.
Recognize"match two groups under a per-pair tolerance, each element usable once" → sort both, one pointer each, three-way branch.

2 · Sort + fixed-k value search

Find k elements hitting an exact target, with k a small constant. The move is always to spend nested loops on \(k-2\) of them and solve the remaining 2-sum in better than linear time — by converging pointers on a sorted array, or by a hash/tree map of pair sums. The trap in both is index bookkeeping: the answer is positions, not values, and every position must be distinct.

Sum of Three Values

\(O(n^{2})\)
The ask

Question. You are given an array of \(n\) integers and a target \(x\). Find three values at distinct positions whose sum is \(x\), and print their positions (1-based, any valid answer). Print IMPOSSIBLE if there is none.

Input
\(n,\ x\), then \(a_1, \dots, a_n\).
Output
Three positions, or IMPOSSIBLE.
Limits
\(1 \le n \le 5000,\ \ 1 \le x, a_i \le 10^9\)
Sample
\(x = 8\), 2 7 5 1 → 1 3 4 (\(2 + 5 + 1\))
Breakdown
  1. State it exactly: \[ \text{find } i \lt j \lt k \ \text{ with } \ a_i + a_j + a_k = x \]
  2. Sort the values, keeping each value's original position. Fix the smallest of the three, \(a_i\). What remains is a two-value problem on the part to its right: \[ a_j + a_k = x - a_i, \qquad i \lt j \lt k \]
  3. On sorted data, two pointers \(l = i+1,\ r = n-1\) solve it. Let \(s = a_l + a_r\): \[ s \lt x - a_i \Rightarrow l{+}{+}, \qquad s \gt x - a_i \Rightarrow r{-}{-}, \qquad s = x - a_i \Rightarrow \text{found} \]
  4. Simplest form: \(n\) choices of \(i\), each followed by one linear scan, so \(O(n^2)\) in total.
Key observations
  1. Sorting loses the original positions, which the output needs. So store each value with its index, as pair<value, index>, and sort by value only.
  2. Fix the smallest of the three, \(a_i\). What remains is two-sum for \(x - a_i\) on the sorted suffix \([i+1,\ n-1]\).
  3. Two-sum on sorted data is a converging scan. If the sum is too small, only raising the low end helps (l++). If it is too big, only lowering the high end helps (r--). Neither move skips a real solution.
  4. Starting \(l\) at \(i + 1\) makes the three positions distinct automatically.
  5. Repeated values cause no trouble, because the scan compares sums, not values.
Brute force → why it dies
naiveThree nested loops over all triples.
cost \(O(n^3)\).
dies at \(n = 5000\) gives \(\binom{n}{3} \approx 2\cdot 10^{10}\) triples, far past a 1 s limit.
therefore Sort with indices, fix one value, replace the inner two loops with a two-pointer scan: \(O(n^2)\) \(\approx 2.5\cdot 10^7\).
Diagram
Implementation

The comparator sorts on .fr alone, so equal values keep an arbitrary index order, which is harmless. The commented-out block below solve() is the abandoned 2-sum-by-map attempt, left in the file.

Sum of Four Values

\(O(n^{2} \log n)\)
The ask

Question. You are given an array of \(n\) integers and a target \(x\). Find four values at distinct positions whose sum is \(x\), and print their positions (1-based, any valid answer). Print IMPOSSIBLE if there is none.

Input
\(n,\ x\), then \(a_1, \dots, a_n\).
Output
Four positions, or IMPOSSIBLE.
Limits
\(1 \le n \le 1000,\ \ 1 \le x, a_i \le 10^9\)
Sample
\(x = 15\), 3 2 5 8 1 3 2 3 → 2 4 6 7 (\(2 + 8 + 3 + 2\))
Breakdown
  1. State it exactly: \[ \text{find } p \lt q \lt r \lt s \ \text{ with } \ a_p + a_q + a_r + a_s = x \]
  2. Group the four into two pairs. Then it is two-sum over pair sums: \[ \underbrace{(a_p + a_q)}_{\text{pair 1}} + \underbrace{(a_r + a_s)}_{\text{pair 2}} = x \]
  3. There are only \(\binom{n}{2} \approx 5\cdot 10^5\) pairs. Store, for each pair sum \(t\), one pair of indices \(m[t] = (i, j)\).
  4. Simplest form: for each pair \((p, q)\), look up the complement and check the four indices are distinct: \[ (r, s) = m\big[x - a_p - a_q\big], \qquad \{p, q\} \cap \{r, s\} = \varnothing \]
Key observations
  1. Split the four values into two pairs. Four-sum becomes two-sum over pair sums, and there are only about \(n^2/2\) pairs.
  2. One stored pair per sum is enough. m[s] is overwritten as the loops run, so it ends up holding the lexicographically largest pair \((i, j)\) with that sum.
  3. That is why overwriting is safe. For an answer \(p \lt q \lt r \lt s\), when the outer loop reaches \((p, q)\), the stored pair for \(x - a_p - a_q\) is \(\ge (r, s)\), so both its indices are \(\gt q\) and it is disjoint from \((p, q)\).
  4. The four-index distinctness check is still needed. An earlier pair can find a stored pair that shares an index with it, and that candidate must be rejected.
  5. The array is stored 1-based, so the indices in the map are already in output format.
Brute force → why it dies
naiveFour nested loops over all quadruples.
cost \(O(n^4)\).
dies at \(n = 1000\) gives about \(10^{12}\) quadruples. Fixing two and two-pointering the rest is \(O(n^3)\) \(= 10^9\), still too slow.
therefore Store every pair sum in a map, then scan the pairs again looking up the complement: \(O(n^2 \log n)\), with \(O(n^2)\) memory.
Diagram
Implementation

Two identical double loops: the first fills m[v[i]+v[j]] = {i,j} for every pair, the second re-walks the same pairs and looks up \(x - \text{sum}\). The line that looks like a bug — blindly overwriting m[sum] — is the one observation 3 defends. The map is std::map, not unordered_map: ordered containers are immune to the CSES anti-hash test, and log n on \(5\cdot 10^{5}\) entries is affordable.

Sum of Two Values

\(O(n \log n)\)
The ask

Question. You are given an array of \(n\) integers and a target \(x\). Find two values at distinct positions whose sum is \(x\), and print their positions (1-based, any valid answer). Print IMPOSSIBLE if there is none.

  2. A map from value to position answers "does the partner exist?" in \(O(\log n)\).
  3. Storing the last position of each value handles \(a_i = x/2\): the first copy finds the last copy, which is a different position.

3 · Sort + single-pass greedy

Sort once, then one forward pass carrying a single scalar — the median, the reachable range R, a running total — decides the answer outright. No second pointer, no table. The recurring shape is that the sorted order makes a local test globally conclusive: the first failure is permanent (Missing Coin Sum), or the quantity being compared is the same at every step (Reducing Dishes).

Stick Lengths

\(O(n \log n)\)
The ask

Question. There are \(n\) sticks with lengths \(p_1, \dots, p_n\). You want all sticks to have the same length. Changing a stick's length by \(1\) (longer or shorter) costs \(1\). What is the minimum total cost?

Input
\(n\), then \(p_1, \dots, p_n\).
Output
One integer: the minimum total cost.
Limits
\(1 \le n \le 2\cdot 10^5,\ \ 1 \le p_i \le 10^9\)
Sample
2 3 1 5 2 → 5
Breakdown
  1. State it exactly: pick a target length \(t\): \[ \min_{t} \; f(t), \qquad f(t) = \sum_{i=1}^{n} |p_i - t| \]
  2. Sort the lengths: \(p_1 \le \dots \le p_n\). Pair the smallest with the largest, the second smallest with the second largest, and so on. For one pair: \[ |p_i - t| + |p_{n+1-i} - t| \;\ge\; p_{n+1-i} - p_i, \quad \text{with equality iff } p_i \le t \le p_{n+1-i} \]
  3. These intervals are nested inside each other, so one \(t\) in the innermost interval reaches every lower bound at once. The innermost interval contains the median.
  4. Simplest form, 0-based after sorting: \[ t = p_{\lfloor n/2 \rfloor}, \qquad \text{ans} = \sum_{i} \big| p_i - p_{\lfloor n/2 \rfloor} \big| \] Sample: sorted \(1,2,2,3,5\), median \(2\), cost \(1+0+0+1+3 = 5\).
Key observations
  1. Sort, then pair smallest with largest. Any \(t\) inside \([p_i,\ p_{n+1-i}]\) pays exactly that pair's width. Any \(t\) outside pays more.
  2. Those intervals are nested, so one \(t\) in the innermost one is optimal for every pair at the same time.
  3. The innermost interval holds the median. \(p_{\lfloor n/2 \rfloor}\) (0-based) lies in it for both odd and even \(n\).
  4. For even \(n\), every point between the two middle values costs the same. No averaging and no floating point is needed.
  5. The mean is the wrong answer. It minimises \(\sum (p_i - t)^2\), not \(\sum |p_i - t|\).
Brute force → why it dies
naiveTry every candidate target (every stick length, or every value in the range) and sum the costs.
cost \(O(n^2)\) over stick lengths; \(O(n \cdot \max p)\) over the value range.
dies at \(n = 2\cdot 10^5\) gives \(4\cdot 10^{10}\). Over the range \(p_i \le 10^9\) it is hopeless. The answer can reach about \(2\cdot 10^{14}\), past int.
therefore The best target is the median: sort, read \(p_{\lfloor n/2 \rfloor}\), sum once. \(O(n \log n)\), sum in long long.
Diagram
Implementation

Three lines after the sort: take p[n/2], sum abs(p[i] - median), print. median is declared long long so p[i] - median is a 64-bit subtraction and abs resolves to the long long overload — the one line a reader would gloss over, and the one that silently truncates if the type is int.

Missing Coin Sum

\(O(n \log n)\)
The ask

Question. You have \(n\) coins with positive integer values. What is the smallest positive sum that you cannot make using a subset of the coins?

Input
\(n\), then \(x_1, \dots, x_n\).
Output
One integer: the smallest sum that cannot be made.
Limits
\(1 \le n \le 2\cdot 10^5,\ \ 1 \le x_i \le 10^9\)
Sample
2 9 1 2 7 → 6
Breakdown
  1. State it exactly: \[ \text{ans} = \min \Big\{\, s \ge 1 : \text{no subset } S \text{ has } \sum_{c \in S} c = s \,\Big\} \]
  2. Sort the coins ascending. Claim: after processing some prefix, the sums you can make are exactly \(\{0, 1, \dots, R\}\). At the start \(R = 0\).
  3. Add the next coin \(c\). The new sums are the old ones plus the old ones shifted by \(c\): \[ [0, R] \,\cup\, [c,\ R + c] \;=\; [0,\ R + c] \quad \text{iff} \quad c \le R + 1 \]
  4. Simplest form: if \(c \gt R + 1\), the sum \(R + 1\) can never be made, because every remaining coin is \(\ge c\). So: \[ \text{for } c \text{ in sorted order: } \ \text{if } c \gt R + 1 \text{ stop; else } R \leftarrow R + c. \qquad \text{ans} = R + 1 \] Sample: sorted \(1,2,2,7,9\) gives \(R = 1, 3, 5\); then \(7 \gt 6\), so the answer is \(6\).
Key observations
  1. Sort ascending and keep one fact true: the sums made so far are exactly the range \([0, R]\).
  2. The next coin \(c\) keeps the range unbroken iff \(c \le R + 1\), and the new range is \([0, R + c]\). Equality counts: \(c = R + 1\) closes the gap exactly.
  3. If \(c \gt R + 1\), then \(R + 1\) cannot be made now. Every later coin is \(\ge c\), so it stays impossible. Stop: the answer is \(R + 1\).
  4. Running out of coins leads to the same answer, \(R + 1\). So the print sits after the loop and covers both exits.
  5. Sorting is what makes the early stop correct. Unsorted, a later small coin could still fill the gap.
Brute force → why it dies
naiveMark every reachable sum: list all subsets, or run a yes/no subset-sum DP over \([0, \sum x]\).
cost \(O(2^n)\) for subsets, \(O(n \cdot \sum x)\) for the DP.
dies at \(n = 2\cdot 10^5,\ x_i \le 10^9\) means \(\sum x\) up to \(2\cdot 10^{14}\) DP cells. That cannot even be stored.
therefore The reachable set is always one interval, so store only its right end \(R\): \(O(n \log n)\), \(O(1)\) beyond the input.
Diagram
Implementation

The loop is a guard and an accumulation, and the answer is printed after it — so the break path and the ran-out-of-coins path share one line of output. The test is strict x[i] > r + 1; the coins are never re-examined and R is the only state.

Reducing Dishes

\(O(n \log n)\)
The ask

Question. A chef has \(n\) dishes. Dish \(i\) has satisfaction \(a_i\), which can be negative. The chef picks any subset of dishes (possibly none) and cooks them in any order, one per time unit. If a dish is cooked \(k\)-th (counting from 1), it scores \(k \cdot a_i\). Maximise the total score. There are \(T\) test cases.

Input
\(T\); for each case \(n\), then \(a_1, \dots, a_n\).
Output
For each case, the maximum total score.
Limits
\(1 \le n \le 500,\ \ -1000 \le a_i \le 1000\) (LeetCode 1402)
Sample
[-2,-2,0,3,2] → 17; [-2,0,-2,3] → 7; [-2,3,-2,0,1,2] → 26
Breakdown
  1. State it exactly: choose a subset \(S\) and an order \(\sigma\) of it: \[ \max_{S,\ \sigma} \; \sum_{k=1}^{|S|} k \cdot a_{\sigma(k)} \]
  2. For a fixed subset, cook in ascending order. If two neighbours are out of order, \(u \gt v\) at positions \(k, k+1\), swapping them changes the score by \[ \big(k v + (k{+}1) u\big) - \big(k u + (k{+}1) v\big) = u - v \gt 0 \]
  3. So sort \(a\) ascending. The best subset keeps a suffix \(a_i, \dots, a_n\): never drop a dish while keeping a smaller one. Dropping the current front dish lowers every remaining multiplier by \(1\): \[ F_{\text{new}} = F_{\text{old}} - T, \qquad T = \sum_{\text{kept}} a \ \ (\text{the front dish included}) \]
  4. Simplest form: the decision depends only on the sign of \(T\): \[ \text{while } T \lt 0:\ \ F \leftarrow F - T,\ \ T \leftarrow T - a_{\text{front}},\ \ \text{drop the front} \]
Key observations
  1. For a fixed subset, ascending order is best. Swapping an out-of-order neighbouring pair gains exactly their difference.
  2. So the only choice left is which dishes to drop, and the dropped ones are always a prefix of the sorted array. Never drop a dish while keeping a smaller one.
  3. Dropping the front lowers every remaining multiplier by one, so the score changes by exactly \(-T\), where \(T\) is the sum of the dishes currently kept.
  4. So the decision depends only on the sign of \(T\): drop while \(T \lt 0\), and stop as soon as \(T \ge 0\).
  5. If \(T\) stays negative to the end, the score reaches \(0\), the empty subset, without any special case in the code.
Brute force → why it dies
naiveTry every subset, sort it, score it. Or a take/skip DP over (index, number already cooked).
cost \(O(2^n \cdot n)\) for subsets; \(O(n^2)\) for the DP.
dies at \(n = 500\) makes \(2^n\) impossible. The \(O(n^2)\) table survives, but it is rebuilt for every test case.
therefore The \(-T\) rule replaces the table: sort, one scoring pass, one dropping pass. \(O(n \log n)\), \(O(1)\) beyond the array.
Diagram
Implementation

The weighted sum is computed once for the full array, then the popping loop edits it in place. The order inside the loop matters: ans -= total; uses the total including the element about to leave, and only then does total -= a[start] remove it. Swapping those two lines applies the wrong delta on the very first pop.

arrays/Reducing_Dishes.cppverbatim
// Problem: Reducing Dishes
// Pattern: sort ascending, then pop the smallest from the front while the
//          running total of included elements is negative
// Time: O(N log N)  Space: O(N)
//
// n dishes with satisfaction[i] (can be negative). Chef picks any subset
// (possibly empty/all) and any cooking order; each dish takes 1 time unit.
// If a dish is the k-th one cooked (1-indexed), its like-time coefficient is
// k * satisfaction[i]. Maximize the total sum over the chosen subset+order.
// T test cases.
//
// Example:
//     [-2,-2,0,3,2]    -> 17
//         [-2,0,-2,3]      -> 7
//         [-2,3,-2,0,1,2]  -> 26

#include <iostream>
#include <vector>
#include <algorithm>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(0); cout.tie(0);

    int t; cin >> t;
    while (t--) {
        int n; cin >> n;
        vector<long long> a(n);
        for (int i = 0; i < n; i++) cin >> a[i];

        sort(a.begin(), a.end());

        long long ans = 0, total = 0;
        for (int i = 0; i < n; i++) {
            ans += (long long)(i + 1) * a[i];
            total += a[i];
        }

        int start = 0;
        while (start < n && total < 0) {
            ans -= total;
            total -= a[start];
            start++;
        }

        cout << ans << '\n';
    }
    return 0;
}
import sys
tok = iter(sys.stdin.read().split())

def main():
    out = []
    t = int(next(tok))
    for _ in range(t):
        n = int(next(tok))
        a = [int(next(tok)) for _ in range(n)]

        a.sort()

        ans, total = 0, 0
        for i in range(n):
            ans += (i + 1) * a[i]           # no (long long) cast: Python ints are unbounded
            total += a[i]

        start = 0
        while start < n and total < 0:
            ans -= total
            total -= a[start]
            start += 1

        out.append(ans)
    print('\n'.join(map(str, out)))

Recognize"pick a subset and an order, score is position × value, elements may be dropped" → sort ascending, pop the front while the running total is negative.

Tasks and Deadlines

\(O(n \log n)\)
The ask

Question. You must process \(n\) tasks one after another, starting at time \(0\). Task \(i\) takes \(a_i\) time units and has deadline \(d_i\). If it finishes at time \(f_i\), you get reward \(d_i - f_i\), which may be negative. Every task must be processed. What is the maximum total reward?

Input
\(n\), then \(n\) lines \(a_i\ d_i\).
Output
One integer: the maximum total reward.
Limits
\(1 \le n \le 2\cdot 10^5,\ \ 1 \le a_i, d_i \le 10^6\)
Sample
(6,10) (8,15) (5,12) → 2
Breakdown
  1. State it exactly and split the sum: \[ \max \sum_{i} (d_i - f_i) \;=\; \sum_i d_i \;-\; \min \sum_i f_i \]
  2. \(\sum d_i\) does not depend on the order. So only \(\sum f_i\) matters. If the tasks run in order \(\sigma(1), \dots, \sigma(n)\), the \(k\)-th one finishes at \(a_{\sigma(1)} + \dots + a_{\sigma(k)}\), so \[ \sum_i f_i = \sum_{k=1}^{n} (n - k + 1)\, a_{\sigma(k)} \]
  3. The earliest task is counted the most times, so it should be the shortest. Swapping neighbours \(u, v\) shows it: \(u\) first costs \(2a_u + a_v\), \(v\) first costs \(a_u + 2a_v\).
  4. Simplest form: sort by duration ascending (deadlines ignored): \[ \text{ans} = \sum_i d_i - \sum_{k=1}^{n} \big( a_{(1)} + \dots + a_{(k)} \big) \] Sample: durations \(5, 6, 8\) finish at \(5, 11, 19\). So \(37 - 35 = 2\).
Key observations
  1. \(\sum d_i\) does not depend on the order. The deadlines are a constant, so only \(\sum f_i\) is optimised.
  2. \(\sum f_i\) is the sum of the running totals of durations, so the task placed \(k\)-th is counted \(n - k + 1\) times.
  3. Swap argument: neighbours \(u\) then \(v\) cost \(2a_u + a_v\); \(v\) then \(u\) cost \(a_u + 2a_v\). Putting the shorter first is never worse. Shortest job first; deadlines are ignored.
  4. Sorting by deadline is the wrong greedy here. That minimises lateness, not the sum of finishing times.
  5. Rewards may be negative. Nothing is filtered out or skipped.
Brute force → why it dies
naiveTry every order and score it.
cost \(O(n! \cdot n)\).
dies at \(n = 2\cdot 10^5\): factorial. Even an \(O(n^2)\) improve-by-swapping loop is \(4\cdot 10^{10}\).
therefore The swap rule depends on durations only: sort ascending, add the running totals, subtract. \(O(n \log n)\), answer in long long (up to about \(2\cdot 10^{16}\)).
Diagram
Implementation

Deadlines are never stored: d starts life as \(\sum d_{i}\) while reading input, then the same variable is decremented by each finishing time and printed as the answer. f[i] += f[i-1] converts the sorted durations into finishing times in place — after that loop f is no longer durations, which is the line to read twice.

Movie Festival

\(O(n \log n)\)
The ask

Question. A festival shows \(n\) movies. Movie \(i\) starts at \(a_i\) and ends at \(b_i\). What is the largest number of movies you can watch completely? You can start a movie at the exact moment another one ends.

Input
\(n\), then \(n\) lines \(a_i\ b_i\).
Output
One integer: the maximum number of movies.
Limits
\(1 \le n \le 2\cdot 10^5,\ \ 1 \le a_i \lt b_i \le 10^9\)
Sample
(3,5) (4,9) (5,8) → 2
Breakdown
  1. State it exactly: \[ \max |S| \quad \text{subject to} \quad b_i \le a_j \ \text{ or } \ b_j \le a_i \ \ \text{for all } i \ne j \in S \]
  2. Take first the movie that ends earliest. In any optimal plan, its first movie can be replaced by this one: it ends no later, so nothing after it breaks.
  3. After that choice, the same problem repeats on the movies with \(a_j \ge\) the chosen end.
  4. Simplest form: sort by end time, keep the end of the last movie watched: \[ \text{if } a_i \ge \text{last}: \ \ \text{count}{+}{+},\ \ \text{last} \leftarrow b_i \]
Key observations
  1. Take first the movie that ends earliest. Any optimal plan can swap its first movie for this one without losing anything.
  2. After that choice, the problem repeats on the movies that start at or after its end.
  3. With the movies sorted by end time, that repetition is one pass carrying last.
Brute force → why it dies
naiveTry every subset and keep the largest one with no overlaps.

4 · Exchange-argument scheduling

One problem, kept separate because the reasoning is the opposite direction to family 3: instead of sorting and reading off the answer, you write down the lower bounds the schedule must obey, then show a schedule that meets them all at once. When that works the sort disappears entirely and the answer is a closed form.

Reading Books

\(O(n)\)
The ask

Question. There are \(n\) books, and two people must each read all of them. Book \(i\) takes \(t_i\) time units. Each person reads a book from start to end without breaks, and both cannot read the same book at the same time. What is the minimum time until both have finished?

Input
\(n\), then \(t_1, \dots, t_n\).
Output
One integer: the minimum total time.
Limits
\(1 \le n \le 2\cdot 10^5,\ \ 1 \le t_i \le 10^9\)
Sample
2 8 3 → 16
Breakdown
  1. Let \(S = \sum_i t_i\) and \(M = \max_i t_i\). Two lower bounds hold for any schedule: \[ T \ge S \ \ (\text{each person reads everything}), \qquad T \ge 2M \ \ (\text{the longest book is read twice, never at once}) \]
  2. If \(2M \ge S\): person 1 reads the longest book first, then the rest. Person 2 reads the rest first, waits, then reads the longest book during \([M, 2M]\). Both finish by \(2M\), and no book is read twice at once.
  3. If \(2M \le S\): put the longest book last. Person 1 reads \(1, 2, \dots, n\). Person 2 reads book \(n\) first, then \(1, \dots, n-1\). Book \(i \lt n\) is read during \([P, P + t_i]\) and \([M + P, M + P + t_i]\), which do not overlap because \(t_i \le M\). Both finish at \(S\).
  4. Simplest form, both bounds are reached: \[ T = \max\big(S,\ 2M\big) \] Sample: \(S = 13,\ M = 8\), so \(T = \max(13, 16) = 16\).
Key observations
  1. Bound A, total work: each person spends \(S = \sum t\), so \(T \ge S\).
  2. Bound B: the longest book is read twice and the two readings cannot overlap, so \(T \ge 2M\).
  3. If \(2M \ge S\): person 1 reads the longest book first and person 2 reads it last. Everything else fits around it, so \(T = 2M\).
  4. If \(2M \le S\): person 2 starts with the longest book and then follows person 1's order. Every other book is shorter than that head start, so they never clash, and \(T = S\).
  5. Both bounds can be reached, so the answer is exactly \(\max(S, 2M)\). No sort and no schedule is needed in the code.
Brute force → why it dies
naiveSearch over both people's orders (and waiting gaps) for the earliest finish.
cost \(O((n!)^2)\) pairs of orders, each needing an overlap check.
dies at \(n = 2\cdot 10^5\): no search is possible at this size, and even sorting is more than needed.
therefore Two lower bounds, both reachable: one pass keeping \(S\) and \(M\). \(O(n)\) time, \(O(1)\) space, totals in long long.
Diagram
Implementation

One read loop maintaining two scalars, then a single max. No array is stored and nothing is sorted — the input is consumed as it arrives. m is seeded at 0, which is safe only because \(t_{i} \ge 1\).
